ECR Verifier: how it works and why

How the system proves, employee by employee, that the PF and ESIC deducted from contract workers' pay actually reached EPFO and ESIC. It covers the problem, the documents, the architecture, the name-matching tolerance, worked examples from the real sample, practice exercises and review questions.

1Purpose & the problem it solves

Vendor agencies supply contract staff and deduct statutory contributions from their wages: PF (12%) and ESIC (0.75%). The company must confirm those deductions were really deposited with the authorities. If they weren't, workers lose benefits and the principal employer carries the liability.

Today

A compliance person matches hundreds of rows across a wagesheet and two government PDFs by hand, every month, for every vendor.

The question per employee

Is the right identifier in the ECR, is it the right person, and was the right amount deposited? Separately for PF and ESIC.

The hard part

Names vary (spelling, word order, honorifics), but some "small" differences are genuinely different people. Catch real mismatches without crying wolf.

3The core idea

  1. Read the PDFs by position, guided by their headers, never by fixed coordinates, so any page count and layout shift works.
  2. Prove the read: parsed rows must add up to the totals the ECR itself prints. If they don't, the report says so in red.
  3. Identify by ID, confirm by name: UAN / IP Number decides who; the name only confirms it's the same person.
  4. Explain every verdict in plain words, with the evidence (both names, both amounts, the statutory expectation).
No AI in the verdict path. Compliance answers must be reproducible and auditable: the same files always give the same report. A local LLM is available only as an optional, labelled second-opinion note on borderline names.

4Architecture

One entry point (run.js → runVerification) is shared by the UI, the CLI, the tests and the evaluator.

5Reading the PDFs (no hard-coding)

  1. Positioned words per page (pdfjs-dist), grouped into lines.
  2. Header line found by anchor keywords. Fragments 16 pt above or below are merged: Name as per + UAN Repository.
  3. Cell → column: biggest header overlap; else, for numbers, right-edge rule (right-aligned); else, nearest header centre.
  4. Data row only if the ID cell has the ID shape, so repeated headers, footers and totals are skipped for free.
  5. Continuation pages reuse the last header's columns; wrapped names are re-joined.

6Reconciliation: the parse proves itself

Each ECR prints its own totals. After parsing, the system recomputes them from the rows:

7Name tolerance: the heart of the problem

  1. Normalise: uppercase, drop punctuation, honorifics (SMT, MR, SHRI…), relation suffixes (S/O…), expand abbreviations (MOHD→MOHAMMAD, KR→KUMAR).
  2. Match tokens: exact · same phonetic key (POOJA≈PUJA, KAVITHA≈KAVITA) · one inserted/deleted letter on 5+ letter words · initial.
  3. Align the shorter name's tokens one-to-one to the longer's (best total score). Any unmatched token → mismatch.
  4. Given-name guard: if initials or extra name parts are involved, at least one matched word must be distinctive (not KUMAR, DEVI, SHARMA, PRASAD…).

Why not one fuzzy score? token_sort_ratio("REKHA SHARMA", "RENU SHARMA") ≈ 0.8, which is above most thresholds, yet it's a different person. A shared surname inflates the score. Rules can say which part differs, and they're testable pair by pair.

8Amounts

  • Compare wagesheet PF @12% ↔ EE share; ESIC @0.75% ↔ IP contribution.
  • Equal when |ECR − wagesheet| ≤ ₹1, because EPFO rounds to the nearest rupee and ESIC rounds up (11,440 × 0.75% = 85.80 → ₹86).
  • Difference = ECR − wagesheet (negative = short).
  • Evidence: statutory rate × ECR wages tells you which side is wrong. VIKRAM: 12% × 13,780 = 1,654 = wagesheet, so the deposit of 1,354 is short.

9Verdict gates (first match wins)

  1. ID blank or malformed in the wagesheet → MISSING (or NOT_APPLICABLE if nothing was deducted)
  2. ID not in the ECR → MISSING with the amount at risk (or NOT_APPLICABLE)
  3. Name is a different person → NAME_MISMATCH (the amount gap is still reported)
  4. Amount differs by more than ₹1 → AMOUNT_MISMATCH with both values, the difference and the expectation
  5. Otherwise MATCHED (notes any variant or rounding)

11How it was tested

54 unit tests

39 labelled name pairs (variants and traps), every verdict gate, amounts, ID formats, and the sample end to end (24/24).

Synthetic scale sets

A generator builds multi-page ECRs plus an answer key with injected variants, look-alike names, shortfalls, missing/extra/blank IDs and wrapped names.

Results

1,500 employees (34/38 pages): 3,000/3,000. 8,000 employees (175/197 pages): 16,000/16,000 in about 3 s. 0 missed mismatches, 0 false alarms.

12Trade-offs & known limits

  • Scanned PDFs are refused (no OCR yet). Reconciliation would be the guard if OCR were added.
  • Header synonyms cover the seen layouts. A renamed column needs one regex added; reconciliation reveals gaps.
  • Nicknames and rare transliterations become NAME_MISMATCH, which is safe but needs a human.
  • The rules are tuned for Indian names (common-surname list, phonetic map).
  • Only the employee share is verified (as the brief asks). Employer share, wage ceilings and NCP checks are extensions.
  • The synthetic tests use variations I designed. They prove scale, not real-world coverage.

13What to practise

Level 1: run and read

  • npm test; read names.test.js and predict three results before running.
  • Run the sample in the UI; open the .xlsx and explain every non-matched row from its reason column.
  • npm run generate -- --n 300 then npm run eval; open outputs/eval.md.

Level 2: change behaviour safely

  • Make R. KUMAR SHARMA acceptable (ALLOW_INITIAL_ONLY) and see which tests change.
  • Add the abbreviation SHK → SHEIKH with a test pair.
  • Add an employer-share check for PF (ER is already parsed) as a note or new verdict, plus workbook columns.
  • Rename a header in the generator (e.g. "EE" → "Employee Share") and confirm the parser still works or needs a synonym.

Level 3: think like a reviewer

  • Break the parser on purpose (shift a column in the generator) and watch reconciliation catch it.
  • Design an OCR fallback for scanned ECRs. Where would errors enter, and how would reconciliation limit the damage?
  • Sketch a reviewer workflow that learns approved name pairs per vendor without weakening the rules.

14Review questions (with answers)

BWhat does the system verify, in one sentence?

For each wagesheet employee, separately for PF and ESIC, that the identifier exists in the authority's ECR, the name belongs to the same person, and the deposited employee share equals the deducted amount (±₹1), with a reason for every verdict.

BWhy is the ID the key and not the name?

UAN and IP Number are unique statutory identifiers. Names repeat and vary. So the ID decides who the ECR row is, and the name only confirms it. Matching by name first would pair the wrong people.

BWhat's the difference between MISSING and NOT_APPLICABLE?

Both mean the ID isn't in the ECR. MISSING means money was deducted, so there's a deposit at risk. NOT_APPLICABLE means nothing was deducted (e.g. above the ESIC wage ceiling), so there's nothing to deposit.

IWhy can't a simple line-by-line regex parse the PF ECR?

The two name columns sit side by side, so the text reads ANIL KUMAR ANIL KUMAR and there's no way to know where one name ends. Positions solve it: each word belongs to the column whose header it sits under.

IHow does the system cope with a 300-page ECR it has never seen?

It finds headers by keywords on every page, reuses columns on continuation pages, accepts only ID-shaped rows, and re-joins wrapped names. Then it reconciles parsed rows and sums against the ECR's printed totals. Tested on 175- and 197-page synthetic ECRs (16,000/16,000 correct in about 3 s).

IWhy is RAJESH vs RAKESH a mismatch when POOJA vs PUJA is a match?

POOJA/PUJA share a phonetic key (OO→U), a known transliteration variant. RAJESH/RAKESH differ by a substitution, J→K, which makes a different common name. Typo tolerance is limited to an inserted or deleted letter on longer words, so substitutions only pass through the phonetic rules.

IWhat is the given-name guard?

When a match relies on initials or ignores extra name parts, at least one matched word must be distinctive, not a very common surname like KUMAR, SHARMA or PRASAD. It stops "DINESH PRASAD" matching "DEVENDRA PRASAD" through the shared surname.

IWhy compare against both PF names?

"Name as per UAN Repository" is the KYC-verified name; "Name as per ECR" is what the employer typed that month. Either legitimately identifies the member, so the best match wins and the report says which matched.

AWhy ±₹1 and not exact equality?

Statutory rounding: EPFO rounds to the nearest rupee and ESIC rounds up. A wagesheet computed with decimals can differ by under a rupee without any wrongdoing. ±₹1 removes that noise but still catches any real shortfall. It's configurable.

AReconciliation fails on a real file. What do you do?

The report still opens, with a red banner. Compare printed vs parsed: a row-count gap points to unrecognised rows (new ID format, odd wrapping); a sum gap with the right count points to a column-mapping error. Fix the header synonym or the ID pattern, add the layout to the tests, and re-run.

AWhere would you use AI in this system, and where not?

Not in the verdicts: they must be reproducible and auditable. Good uses: an advisory note on borderline names (implemented, off by default); suggesting column mappings for an unknown wagesheet layout with human confirmation; OCR for scans; summarising a vendor's monthly exceptions for a manager.

AHow would you scale this to all vendors, every month?

Batch runs per vendor and month, results in MongoDB, vendor dashboards (repeat shortfalls, chronic missing IDs), a reviewer queue for name mismatches with remembered approvals, and alerts when a vendor's shortfall exceeds a threshold. The verification core stays the same pure function.
